# Plan 2026-03-11: Paper structure and staged delivery for the Python port + Lui results

## Objective
Prepare a manuscript that does two things clearly and in the right order:
1. Present `linstab2d` as the Python port of the MATLAB `LinStab2D` codebase.
2. Present new physical results from the Lui 2022 case family.

The paper should not read as a Hamada-centered solver paper.
Reproduction and validation are necessary evidence, but they are not the main claim.

## Two coupled projects in one repository
This repository currently carries two tightly linked but distinct projects:
1. The code project:
   1. port the MATLAB code to Python,
   2. verify the implementation,
   3. generate validated artifacts for new cases.
2. The paper project:
   1. explain the ported code,
   2. document the verification/validation ladder,
   3. present the new Lui-based results.

The practical consequence is that not every coding milestone is a paper milestone, and not every manuscript section should drive new coding work.
The plan below keeps these two tracks separate while making their dependencies explicit.

## Locked paper narrative
1. `martini2024` defines the reference MATLAB code and the five shipped example cases.
2. The Python code reproduces those five cases as appendix-level port-verification evidence.
3. A separate validation case is then built from the Robinet 2007 problem using the Song 2023 simulation/baseflow data.
4. The main claim-bearing results are the Lui-based cases, starting with `results/case1`.

## Evidence hierarchy
1. Appendix evidence:
   1. Reproduction of the five Martini/MATLAB example cases.
   2. This establishes port fidelity and implementation traceability.
2. Validation evidence:
   1. One Robinet 2007 case using Song 2023 simulation data.
   2. This shows the Python code behaves correctly on an external benchmark beyond the shipped MATLAB examples.
3. Main results:
   1. Lui Case 1 first.
   2. Cases 2-7 later, as controlled parameter variations (for example Reynolds number, Mach number, mesh).

## Non-negotiable stage gate
Do not move to Lui Cases 2-7 until all three conditions below are satisfied:
1. The five Martini example reproductions are closed honestly enough for the appendix.
2. The Robinet/Song validation case is closed.
3. Lui Case 1 is closed and manuscript-ready.

This gate is meant to prevent the paper from expanding faster than the verification base.

## Current repository situation

2. The appendix material is also still Hamada-oriented in places, instead of being organized around the five Martini reproductions.
3. `results/case1` is the intended first Lui-based result slot, but several files and notes still use Hamada naming and framing.
4. Parsed reference material is already present or being added under `docs/`:
   1. `docs/martini2024/`
   2. `docs/robinet2007.md`
   3. `docs/song2023.*`
   4. `docs/lui2022.*`

## Track split
### Track A: code project
1. Finish and archive the five Martini reproductions.
2. Freeze and validate the Robinet/Song case.
3. Freeze and analyze Lui Case 1.
4. Only then expand to Lui Cases 2-7.

### Track B: paper project
1. Reframe the manuscript around the Python port plus new Lui results.
2. Push the five Martini reproductions into the appendix.
3. Use Robinet/Song as the explicit validation bridge.
4. Use Lui Case 1 as the first main claim-bearing result.

### Shared interface between the two tracks
1. Appendix text depends on Track A closing the five Martini cases honestly.
2. Validation text depends on Track A freezing one Robinet/Song configuration and metric set.
3. Main-results text depends on Track A freezing Lui Case 1 with publication-ready figures and interpretation.
4. Cases 2-7 are blocked both as code work and as paper scope until the earlier gates pass.

## Target manuscript structure
1. Introduction
   1. Motivation for a Python port of `LinStab2D`.
   2. Why sparse/PETSc/SLEPc implementation matters.
   3. What is reproduced from MATLAB and what is new in this paper.
2. Methods / code presentation
   1. Governing formulation and discretization.
   2. Ported architecture: MATLAB reference to Python implementation.
   3. Solver stack and practical workflow.
3. Verification and validation strategy
   1. Explain the three evidence layers: reproduction, validation, new results.
   2. State clearly that reproduced Martini examples are verification evidence, not novelty evidence.
4. Main results
   1. Validation case: Robinet 2007 with Song 2023 baseflow/simulation data.
   2. Lui Case 1 as the first claim-bearing new-physics case.
   3. Hold space for Cases 2-7 only after the gate is passed.
5. Discussion / conclusions
   1. What the port enables.
   2. What the Lui Case 1 result shows physically.
   3. What remains for the full 7-case campaign.
6. Appendix
   1. Five Martini example reproductions.
   2. Reproducibility commands, status tables, and comparison artifacts.

   4. `lui2022`
2. Extract from each reference only what the manuscript needs:

   2. physical parameters
   3. boundary conditions
   4. target observables
   5. figures/tables worth reproducing or comparing against
3. Produce a short internal mapping note:
   1. which reference supports appendix reproduction,
   2. which supports validation,
   3. which supports new-results framing.

## Workstream B: appendix reproduction of the five Martini cases
1. Finalize the status of Examples 0-5 for appendix use.
2. For each example, archive:
   1. Python artifact path
   2. MATLAB reference path
   3. comparison script/report
   4. honest status (`PASS`, `SOFT_FAIL`, `HARD_FAIL`, `UNAVAILABLE`, or a revised taxonomy if explicitly changed)
3. Build appendix-ready outputs:
   1. one summary table across all five cases,
   2. minimal per-case notes on what was compared,
   3. only the figures that are actually needed to support the appendix narrative.
4. Keep the appendix concise:
   1. enough to prove reproduction discipline,
   2. not a second paper inside the paper.

## Workstream C: Robinet 2007 / Song 2023 validation case
1. Define the exact validation target:
   1. which Robinet configuration is being matched,
   2. which Song 2023 simulation/baseflow fields are used,
   3. which observable(s) constitute validation.
2. Freeze one validation configuration in code and config files.
3. Generate manuscript-ready outputs:
   1. validation figure(s),
   2. comparison metric(s),
   3. solver and mesh metadata,
   4. short explanation of what is validated and what is not.
4. This section should read as an external benchmark bridge between appendix reproduction and Lui results.

## Workstream D: Lui Case 1 as the first main result
1. Treat `results/case1` as the first claim-bearing Lui case.
2. Freeze the exact parameter set used for Case 1.
3. Produce only the artifacts needed for publication:
   1. baseflow identification
   2. mesh details
   3. solver configuration
   4. primary stability/resolvent outputs
   5. physics figure(s) and supporting metric(s)
4. Write the result around physical interpretation, not only parity or runtime.
5. Audit naming:
   1. remove or isolate Hamada-specific naming that could confuse the manuscript if Case 1 is genuinely a Lui case.

## Workstream E: staged expansion to Lui Cases 2-7
1. Define the controlled parameter matrix only after Case 1 is closed.
2. Likely variation axes:
   1. Reynolds number
   2. Mach number
   3. mesh resolution
   4. any additional physically justified parameter from Lui 2022
3. Require a short rationale for each added case:
   1. what parameter changes,
   2. why it matters physically,
   3. what comparison to Case 1 it enables.
4. Do not start production of these cases early just because the scripts exist.

## Acceptance gates
1. Gate A: appendix-ready reproduction package
   1. All five Martini examples have documented status and archived comparison artifacts.
   2. The appendix can be written without inventing missing evidence.
2. Gate B: validation closure
   1. The Robinet/Song case has a frozen setup and a clear comparison metric.
   2. The manuscript can explain why this case counts as external validation.
3. Gate C: Case 1 closure
   1. Lui Case 1 has frozen parameters, final figures, and a stable physical interpretation.
   2. The manuscript can state the result without hand-waving.
4. Gate D: expansion permission
   1. Only after Gates A-C pass do Cases 2-7 start.

## Risks and controls
1. Risk: the manuscript drifts back to Hamada because those artifacts are currently the most developed.
   1. Control: keep Hamada as internal development history unless it is explicitly re-scoped into the paper.
2. Risk: appendix reproduction becomes too large and delays the actual paper.
   1. Control: keep only the minimum evidence needed for a defensible appendix.
3. Risk: validation and new-results sections get mixed.
   1. Control: require one explicit sentence in the manuscript stating whether each case is reproduction, validation, or new physics.
4. Risk: Cases 2-7 start before Case 1 is stable.
   1. Control: keep the stage gate explicit in the plan and in coauthor discussions.
