# Plan - manuscript refinement and story framing

Date: 2026-03-01
Target journal: Metascience in Aerospace (AIMS Press)
Paper type: applied computational-methods/software paper

## 1) Core narrative (the story we tell)

Problem:
- `martini2024` MATLAB workflow is scientifically strong but operationally limited for very large refined cases.
- MATLAB `\` is effectively serial/limited for our target scale and constrains memory and parallel execution.

Intervention:
- `linstab2d` reproduces the same linearized compressible stability/resolvent framework in open Python.
- The major change is the solver layer: PETSc/SLEPc + MUMPS/Krylov preconditioned pipelines, designed for fat-node execution.

Outcome claim:
- we preserve the original numerical model behavior,
- we remove MATLAB dependency,
- we unlock larger sparse problems (target up to O(10^6) DOF) with controlled memory/parallel strategies.

Positioning:
- not a new fluid-theory paper,
- an implementation-and-scalability paper with rigorous numerical equivalence and solver engineering.

## 2) Scope and non-scope (to keep text clean)

In scope:
- operator/discretization equivalence to MATLAB reference workflow,
- boundary-condition and curvilinear transformation fidelity,
- stability and resolvent pipelines,
- solver strategy comparison (direct vs iterative),
- performance and memory behavior on representative hardware.

Out of scope:
- claiming new instability physics,
- claiming a universally best linear solver,
- over-claiming unresolved iterative-resolvent paths if still open.

## 3) Manuscript structure to implement

1. Introduction
- frame bottleneck: MATLAB dependency + limited scalability for refined grids.
- define objective: open-source equivalent + scalable sparse linear algebra.
- state contributions in three bullets:
  - full-workflow MATLAB-equivalent implementation in Python,
  - PETSc/SLEPc solver architecture for large sparse systems,
  - reproducible comparisons versus MATLAB and resolvent4py.

2. Governing equations and discrete operators
- keep equations from Martini lineage (cite source).
- show linearized system, block structure, curvilinear mapping terms, BC imposition strategy.
- explicitly distinguish unchanged physics/discretization from changed solver backend.

3. Solver architecture
- Strategy A: robust baseline (MUMPS direct via PETSc).
- Strategy B: scalable path (SLEPc/PETSc iterative, shift-invert/preconditioned Krylov).
- explain memory vs robustness trade-off and failure semantics (strict convergence checks).
- include practical discussion for fat nodes (MPI + threaded BLAS options).

4. Verification and validation design
- verification: operator-level equivalence checks (matrix/operator diagnostics).
- validation: output-level agreement (spectra, gains, leading modes) on shared cases.
- keep parity details concise in main text; push exhaustive per-case artifacts to appendix/supplement.

5. Results
- R1: migrated MATLAB example set summary (compact table).
- R2: Hamada case (stability + resolvent) as bridge from parity to production intent.
- R3: performance/memory solver study:
  - MATLAB vs Python/PETSc,
  - MUMPS vs iterative PETSc within Python stack.
- R4 (optional but valuable): resolvent4py shared example comparison and interoperability framing.

6. Discussion
- what became possible (larger refined problems, reproducible open workflow),
- what remains hard (iterative preconditioning sensitivity, unresolved corners),
- operational guidance: when to use Strategy A vs B.

7. Conclusions
- concise, engineering-focused, evidence-bounded claims.

## 4) Evidence package required for a strong paper

Tables:
- T1: case inventory and coverage (all reference MATLAB examples + Hamada + resolvent4py shared case).
- T2: numerical agreement metrics (eigenvalue/gain/mode error summaries).
- T3: runtime and memory by solver strategy and hardware.
- T4: solver settings ledger (KSP/PC/ST/EPS, tolerances, process/thread counts).

Figures:
- F1: workflow/architecture diagram (MATLAB lineage -> Python operator assembly -> PETSc/SLEPc solvers).
- F2: representative spectrum overlays (Python vs MATLAB).
- F3: leading mode fields/cuts overlay (Python vs MATLAB).
- F4: strong visual of solver scaling behavior (time and memory trends).
- F5: optional resolvent4py comparison on shared benchmark.

Appendix/supplement:
- full parity ledgers, extended spectra/modes, operator diagnostics, run logs, config files.

## 5) Writing rules for clarity and credibility

- never imply "new governing equations"; state that equations/discretization lineage is inherited.
- separate "model fidelity" from "solver performance" in wording and figures.
- all speed claims must include hardware and solver options.
- use hedged language where unresolved.
- avoid promotional tone; emphasize reproducibility and practical limits.
