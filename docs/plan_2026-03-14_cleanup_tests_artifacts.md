Reduce the recent hard-coded file sprawl without deleting evidence, runnable examples, or tests that still carry unique coverage.

This is a cleanup plan only. No source/test deletions are included here.

## Guardrails

- Do not delete claim-bearing artifacts or validation gates during cleanup.
- Keep `results/case1` as the canonical Lui 2022 reference case.
- Do not remove generated example outputs that are still referenced by `paper/supp.tex`, README/docs, or example workflows until replacement paths are explicit.
- Do not delete tests only because they are large; first prove they are redundant, obsolete, or misplaced.
- Do not delete tests only because the source code “looks well coded”.
  Static-looking code can still guard contracts, interface drift, or numerical invariants.
- Treat the root `plan*.md` -> `docs/plan*.md` state as an in-progress move, not as safe garbage.

## Deletion proof standard

No file should be deleted unless the cleanup pass can answer all applicable checks.

### For generated artifacts

At least all of these should be true:

1. the artifact is reproducible
2. it is ignored or intentionally meant to be local-only
3. it has no live reference from source/docs/paper runners
4. it is not part of a claim-bearing or gate-defining result

### For tracked docs/plans

At least all of these should be true:

1. there is one canonical surviving copy
2. duplicate status is confirmed by content, not assumed from the filename
3. any move is represented as a real rename, not delete-plus-add confusion

### For tests

At least one of these must be proven:

1. another retained test covers the same behavior and failure mode
2. the test asserts only an implementation detail with no user-facing or numerical contract value
3. the test checks trivial static structure that is already subsumed by stronger behavioral or end-to-end tests
4. the test protects a path that no longer exists

### Bucket F: weak or low-value tests

This is separate from redundancy. A test can be unique but still low-value.

Review rubric:

#### Weak-test indicators

- only checks shape/length/count for a static helper without checking behavior
- only checks that an object has a method/attribute instead of using it
- only checks literal implementation structure that users do not depend on
- repeats the same assertion pattern across many nearby cases without new behavior
- checks error-message wording where the wording is not part of the contract
- asserts simple pass-through wrapper behavior already guaranteed by a stronger integration test
- exercises only a static or obvious branch with no numerical, API, or workflow risk

#### Current pattern hits worth review

These are review candidates, not immediate delete commands.

- `tests/test_operators.py`
  - several `assert hasattr(...)` checks for PETSc matrix capabilities appear inside tests that already do stronger parity/matvec checks nearby
  - these are prime candidates for pruning if the surrounding behavioral assertions already prove the path
- shape-only and size-only tests in:
  - `tests/test_utils.py`
  - `tests/test_operators.py`
  - `tests/test_linear_operator_harmonic.py`
  - `tests/test_case1_parametric_parity.py`
  - `tests/test_mesh.py`
- pure-count boundary/index checks in:
  - `tests/test_mesh.py`
  - `tests/test_boundary_conditions.py`

Review rule:
- if a shape/count assertion is the only contract for a public return type, it may still be worth keeping
- if it only restates an obvious implementation fact already enforced by downstream behavioral tests, it is a consolidation candidate

#### Strong-test indicators

- guards numerical parity or residuals
- guards MPI ownership/distribution behavior
- guards public API contracts
- protects manuscript/evidence gates
- protects bug fixes or historically broken paths
- proves interoperability across SciPy/PETSc/backends

Action:
- tag each suspect test as `strong`, `weak-but-unique`, `redundant`, or `obsolete`
- delete `weak` tests only when their coverage value is clearly below maintenance cost
- prefer merging weak tests into a smaller number of stronger behavioral tests

## Phases

### Phase 1: inventory and classify

Commands:

- `git status --short`
- `find . -maxdepth 2 \\( -path './.git' -o -path './.venv' \\) -prune -o -type f -mtime -3`
- `git log --since='2026-03-12' --name-only`
- `for f in tests/test_*.py; do wc -l \"$f\"; done | sort -nr`
- `rg` + `shasum` to confirm duplicates and references

Deliverable:
- one table: `path | class | keep/review/remove | reason`
- for tests, extend the table to:
  `path | behavior owner | strong/weak | unique/redundant | proposed action`

### Phase 2: delete low-risk clutter

Targets:

- Bucket A only

Verification:

- `git status --short`
- confirm `.gitignore` covers the recurring clutter

### Phase 3: resolve plan/doc duplicates

Targets:

- Bucket B

Verification:

- root/docs plan files are no longer in ambiguous delete/add state
- exactly one canonical copy remains for each plan artifact

### Phase 4: review generated docs/examples/paper outputs

Targets:

- Buckets C and D

Verification:

- every kept generated artifact has an active reference or an explicit reason to remain
- every deleted artifact is reproducible and non-claim-bearing

### Phase 5: consolidate test surface

Work sequence:

1. map test files to source modules and unique behaviors
2. mark tests as strong, weak, redundant, or obsolete
3. start with weak-pattern pruning inside large files before deleting whole files
4. remove the weak/obsolete tests that have the lowest contract value first
5. merge redundant tests into stronger behavioral tests when possible
6. delete or merge only one cluster at a time
7. rerun the affected suites after each batch

Suggested first weak-test review pass:

1. `tests/test_operators.py`
   - remove or merge low-value `hasattr(...)` checks that sit next to stronger parity assertions
2. `tests/test_utils.py`
   - review shape-only tests for whether they are true public API contracts or just implementation echoes
3. `tests/test_mesh.py` and `tests/test_boundary_conditions.py`
   - review pure-count assertions for whether they provide unique safety beyond stronger behavioral checks

Verification commands:

- `PYTHONPATH=$PWD/src .venv/bin/python -m pytest tests/test_utils.py tests/test_operators.py tests/test_solvers.py tests/test_case1_smoke.py`
- additional targeted nodeids for any cluster being merged or deleted

## Recommended first execution batch

Start with the lowest-risk cleanup first:

1. remove `.DS_Store`, `__pycache__`, `*.pyc`
2. verify which tracked paper/build outputs actually remain tracked
3. decide whether `docs/plan*.md` is the canonical archive location
4. build the strong/weak/redundant map for tests
5. only then audit generated example/doc artifacts that still have live references

## Open decisions

- Are historical plans supposed to live under `docs/` now, or was that move accidental?
- Do you want example `.npz/.png` outputs kept as tracked convenience artifacts, or pushed out of git if they are reproducible?
- For test cleanup, do you want to optimize for:
  - fewer files
  - shorter runtime
  - or clearer claim-to-test mapping
- Should “weak but cheap” tests be kept if they improve readability, or do you want the suite biased toward only high-signal contract tests?

## Definition of done

Cleanup is complete when:

- low-value generated clutter is gone and ignored
- plan/doc duplicates have one canonical location
- generated parse/build artifacts are either justified or removed
- redundant tests are removed only after replacement coverage is verified
- the remaining test/layout tree is smaller and easier to explain
