# Plan: Light-Mesh Solver Now, Scalable Solver for Big Cases

## Objective
Build a solver workflow that:
1. Preserves the current light-mesh MATLAB-parity behavior.
2. Adds a PETSc/SLEPc-native distributed path that can scale to very large operators (toward 1 TB-class problems).

## Success Criteria
1. Light mesh: parity remains pass for Hamada (`pass=True` in spectrum parity artifact).
2. Medium mesh: distributed solver returns stable eigenpairs with bounded memory per rank.
3. Large mesh: no global SciPy matrix materialization, no forced single-rank assembly, MPI path active end-to-end.

## Current Blocking Facts
1. Assembly is currently global SciPy sparse first, then converted to PETSc (`scipy_to_petsc`).
2. Runner currently forces `MPI_PROCS=1`.
3. Shift-invert LU/MUMPS is used by default, which is not the scalable default for extreme sizes.

## Implementation Phases

### Phase 1: Freeze and Protect the Light-Mesh Path
1. Keep current Hamada parity defaults and regression test as the reference baseline.
2. Add explicit solver mode flag:
   - `local_direct` for current path.
   - `distributed_iterative` for scalable path.
3. Keep `local_direct` as default until distributed path is validated.

### Phase 2: Introduce Distributed Matrix Assembly (No Global SciPy Matrix)
1. Add distributed PETSc AIJ assembly utilities in `linstab2d/utils/petsc_core.py`.
2. Implement ownership-range aware row assembly using PETSc row insertion APIs.
3. Refactor operator assembly to provide local row contributions without constructing full SciPy `L0`.
4. Ensure BC application also works in distributed row-ownership mode.
5. Keep exact same algebra and ordering as local mode.

### Phase 3: Scalable Eigensolve Path
1. In `linstab2d/solvers/eigenvalue.py`, add distributed solver configuration for big problems.
2. Keep SLEPc EPS for spectrum extraction, but avoid direct LU as default at scale.
3. Use iterative KSP inside ST with scalable preconditioners.
4. Expose runtime options for:
   - `eps_type`, `st_type`, `ksp_type`, `pc_type`
   - subdomain/block settings for MPI runs
5. Keep direct LU/MUMPS available only as optional small/medium debug mode.

### Phase 4: Matrix-Free Option (Required for Extreme Regimes)
1. Add optional PETSc `MatShell` operator path for action-only operator evaluation.
2. Implement `mult(x)->y` using existing differential operators and coefficient fields.
3. Keep assembled distributed AIJ path as intermediate milestone and fallback.
4. Use matrix-free path when memory model predicts assembled AIJ is too large.

### Phase 5: Performance and Memory Instrumentation
1. Emit per-rank memory stats and nnz diagnostics during assembly and solve.
2. Write structured artifacts with:
   - assembly time
   - solve time
   - memory per rank
   - convergence metrics
3. Add simple capacity estimator:
   - expected nnz
   - expected bytes for AIJ
   - recommended rank count

### Phase 6: Validation Ladder
1. Gate A: light mesh parity unchanged (`tests/test_hamada_operator_parity.py` + spectrum parity).
2. Gate B: medium mesh local vs distributed eigenvalue agreement within tolerance.
3. Gate C: increasing-mesh strong-scaling run with memory trend and timing report.
4. Gate D: first big-case production run with documented solver options and convergence evidence.

## Execution Order (Recommended)
1. Phase 1 and Phase 2 first.
2. Phase 3 next, then medium-mesh validation.
3. Phase 4 only after assembled-distributed path is stable.
4. Phase 5 and Phase 6 continuously after each phase.

## Non-Negotiables
1. Do not break current parity path while adding scalability features.
2. No global matrix copies in the scalable path.
3. MPI rank count must be user-controlled and respected.
4. Every scalability claim must include timing and memory evidence artifacts.
